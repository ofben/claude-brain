Mistakes that cause rewrites, broken student experiences, or major trust failures.

### Pitfall 1: Phantom Notes — Lesson Scripts Reference Vault Notes That Don't Exist

**What goes wrong:** Teaching scripts in modules 2.2, 2.3, and 3.5 treat `[[AI as Extended Memory]]`, `[[AI and Creative Work]]`, `[[Client Work Dashboard]]`, and `[[GitLab Async Communication Model]]` as if they already exist in the vault. They don't. Module 2.3 even injects a daily note with these as links already present inside it, making them appear as "things Alex built in earlier modules." A student running modules in sequence will see broken links (Obsidian ghost links) or Claude will try to reference notes it cannot find.

**Why it happens:** AI generated the lesson scripts in one session and referenced notes that would be *created during exercises* as if they were *pre-seeded fixtures*. The generation didn't maintain a consistent ledger of what existed vs. what would be built.

**Consequences:** Student sees orange/red "unresolved link" indicators in Obsidian during level 2. Module 3.5's Inbox Pattern triage script explicitly references `[[AI as Extended Memory]]` as a destination for a capture — Claude will either hallucinate the note or fail to link it correctly.

**Prevention:**
- Audit every `[[link]]` in all 24 lesson scripts against actual vault files at `/Users/benest/dev/claude-brain/vault/`
- For each phantom reference: either create the missing note as a vault fixture, or change the script to create it dynamically during the module where it first appears
- Use the following test: extract all `[[note names]]` from lesson scripts, strip aliases, compare against `vault/**/*.md` filename list

**Detection (warning sign):** When playtesting, if you see Obsidian displaying purple/grey wikilinks that don't resolve on click, you have phantom notes.

**Phase to address:** Content quality review / vault consistency — before playtest.

### Pitfall 2: Frontmatter Tag Format Inconsistency Breaks Teaching Credibility

**What goes wrong:** The vault templates (`06-Templates/Daily Note Template.md`, `Research Note Template.md`, `Draft Template.md`) use scalar string syntax for tags (`tags: daily-note`, `tags: research`, `tags: draft`). But every actual vault note uses array syntax (`tags: [daily]`, `tags: [draft, bloom, digital-minimalism]`). When module 4.2 teaches the auto-organize hook by showing frontmatter examples, or when module 2.1 teaches note types by pointing students to templates, the student sees two incompatible formats with no explanation of which is correct.

**Why it happens:** Templates and vault notes were likely generated by different prompts in the same AI session without a shared schema constraint.

**Consequences:**
- Students create templates-based notes with scalar tags, then module 3.1's "Vault-Aware Claude" reads their vault and finds mixed formats, producing confusing output
- The Librarian agent scanning for "inconsistent tags" will flag the student's own template-based notes as problematic — when the templates are the source of the problem
- Progressive summarization in module 2.4 adds frontmatter layers; if the format differs from existing notes, it erodes "professional polish" that the course promises

**Prevention:**
- Standardize all templates to use array syntax: `tags: [daily-note]`, `tags: [research]`, `tags: [draft]`
- Add a "frontmatter schema" note in `.claude/SCRIPT_INSTRUCTIONS.md` defining the canonical format so future AI runs maintain consistency
- Run a grep audit: `tags: [a-z]` (scalar) vs `tags: \[` (array) across all vault files

**Detection:** Any vault file with `tags: somestring` (no brackets) is using scalar format.

**Phase to address:** Vault consistency pass — before playtest.

### Pitfall 3: Module 2.5 Incomplete Content Will Reach Students

**What goes wrong:** `lesson-modules/2-building-the-brain/2.5-knowledge-graph/CLAUDE.md` contains a `[Note Name]` placeholder at line 135 — the module script says "Let's start with **[Note Name]**." instead of naming a real note. This is verbatim placeholder text that Claude Code will deliver word-for-word to students per the SCRIPT_INSTRUCTIONS.md requirement to follow Say blocks precisely.

**Why it happens:** The AI generation session ended before this module was complete. The `[Note Name]` marker is template scaffolding that was never filled in.

**Consequences:** Student experiences a jarring break in immersion. A module that should feel like Claude "knowing the vault" instead exposes the teaching script scaffolding. This is a fourth-wall break — exactly what SCRIPT_INSTRUCTIONS.md prohibits.

**Prevention:**
- Complete the knowledge graph module: identify which vault orphan notes the script should use for the demo (good candidates: `Quick thought - AI and memory.md`, `Podcast rec from Jamie.md`, `Book idea fragments.md` — these are inbox captures without outbound links)
- If time-constrained: restructure the Action block to dynamically identify orphan notes rather than hardcoding names

**Detection:** Grep for `\[Note Name\]` or similar `\[[A-Z][a-z]+ [A-Z][a-z]+\]` patterns (capitalized words in brackets that aren't wikilinks) across all lesson scripts.

**Phase to address:** Content quality review — this is a hard blocker for distribution.

### Pitfall 4: Stale Hardcoded Dates Will Break the Narrative Immediately

**What goes wrong:** The creator context in `creator-context/PROJECTS.md` and the vault's pre-seeded notes use specific dates: March 15, 20, 21, 22, 25, 27, 28 (2026). Daily notes exist for March 10, 12, 14, 17, 19. The Horizon article deadline is "March 28, 2026." By the time anyone clones this repo in April 2026 or later, Alex is perpetually past deadline. The Bloom "Saturday deadline" (March 22) will have passed. The "send Sarah the revised outline by March 20" follow-up is already overdue.

**Why it happens:** AI generated a realistic fictional scenario anchored to the current date (March 2026). Nobody set these dates to be relative or future-proof.

**Consequences:**
- Module 1.1 introduces Alex as currently juggling deadlines. Students who notice specific past dates will feel the "reality" of the scenario collapse
- Module 4.6 (graduation day-in-the-life) shows Alex using `/daily` to create "today's" note — but the vault's most recent daily note is March 19 and the "current" deadline pressure won't match the student's actual date
- Subtle narrative erosion: Alex feels less real when deadlines are two years in the past

**Prevention:**
- Replace hardcoded dates in vault notes and creator-context with a clearly fictional but undated framing ("last week," "end of this month," "coming Friday") where possible
- For dates that must be specific (daily notes need actual dates), document in README that the vault represents a snapshot from a specific time, not real-time data
- Add note in README: "The vault is pre-loaded with content from a fictional March 2026 — this is a snapshot, not live data"

**Detection:** Any `2026-03` date in vault files that creates a deadline or time-pressure narrative.

**Phase to address:** BASB research integration phase (touches narrative/positioning) and vault consistency pass.

### Pitfall 5: Progressive Summarization Misattributed to Tiago Forte's BASB

**What goes wrong:** Module 2.4 teaches "five layers" of progressive summarization (Capture, Highlight, Summarize, Your Take, Connect). Module 3.4 attributes "progressive summarization" to Tiago Forte explicitly. However, Tiago Forte's original progressive summarization technique has four layers (not five) and the layers are specifically: save the passage, bold the important, highlight the most important, executive summary. The "Your Take" and "Connect" layers are meaningful additions, but they are not Forte's original framework — they blend Zettelkasten's atomic note principles into Forte's concept.

**Why it happens:** AI training data contains many blog posts and community discussions that expand, remix, or misremember Forte's original framework. The generated content blended these secondary sources.

**Consequences:**
- Students who have read BASB or Forte's blog will notice the discrepancy and lose trust in the course's accuracy
- Attributing ideas to Forte that aren't his dilutes the course's credibility as a serious PKM resource
- The course is explicitly positioning itself to "build on BASB concepts" — misrepresentation undermines this positioning

**Prevention:**
- Research Forte's actual progressive summarization layers against official sources before publishing
- Either: (a) correctly attribute Forte's 4-layer framework and label the additional layers as course extensions, or (b) rename the practice to avoid the attribution entirely
- Add clear language like: "Tiago Forte's concept of progressive summarization inspired this approach — we've extended it with two additional layers..."

**Detection:** Cross-reference the module 2.4 layer description against Forte's writing at fortelabs.com. If the layers differ, attribution is wrong.

**Phase to address:** BASB research integration.

### Pitfall 6: The Folder Structure Claims PARA Without Teaching PARA

**What goes wrong:** Module 1.1 mentions "the PARA method" in the common questions section but teaches a folder structure (00-Inbox, 01-Daily-Notes, 02-Projects, 03-Research, 04-Drafts, 05-References, 06-Templates, 07-MOCs, 08-Published) that is NOT PARA. PARA has four categories: Projects, Areas, Resources, Archives. The vault uses eight categories. Several of Alex's vault folders don't map to PARA (Daily Notes, Drafts, Templates, MOCs are not PARA concepts).

**Why it happens:** The course mentions PARA in passing without committing to it, but the folder structure was designed independently and has grown beyond PARA's scope.

**Consequences:**
- Students who look up PARA after module 1.1 will find a 4-folder system and be confused why the vault has 8
- BASB integration work will be harder if there's a fundamental structural mismatch between the course's vault and the framework it claims to draw from

**Prevention:**
- Either commit to PARA alignment (restructure vault and explain where each folder maps) or explicitly differentiate ("we use a more granular structure than PARA because knowledge work for writers needs...")
- Do not mention PARA without a brief explanation of how this vault's structure relates to it
- The module 1.1 answer to "Is this based on a real method?" should acknowledge the differences clearly

**Phase to address:** BASB research integration.

### Pitfall 7: Module Prerequisites Are Implicit — Skip-Around Students Will Fail Silently

**What goes wrong:** Module 2.3's daily note references `[[AI as Extended Memory]]` (created in 2.1) and `[[AI and Creative Work]]` (created in 2.2). Module 3.1 assumes the student has a working CLAUDE.md (created in 1.5). Module 4.5's custom slash commands build on hooks (4.1) and assume `.claude/scripts/` exists (created in 4.2). None of these dependencies are stated anywhere. A student who starts at level 2 (perhaps they're already an Obsidian user) will hit silent failures.

**Why it happens:** Linear course design assumes everyone runs modules in sequence. Teaching scripts were generated assuming perfect sequential execution.

**Consequences:**
- Module 3.5 (Inbox Pattern) explicitly processes notes and creates links to `[[AI as Extended Memory]]` — if that note doesn't exist, Claude will either create a ghost link or fail the triage step
- The hooks module 4.1-4.2 sequence creates a `.claude/scripts/` folder; module 4.5 assumes this exists

**Prevention:**
- Add a brief "Before you start" section to modules 2.1, 3.1, and 4.1 listing assumed vault state
- In the README, note that modules are designed to be run sequentially and skipping modules may cause issues
- Consider adding simple vault-state checks at the start of level-transition modules (start of level 2, start of level 3, start of level 4)

**Detection:** Identify every module that reads a specific vault file by exact name. That vault file is an implicit prerequisite.

**Phase to address:** Playtest validation.

### Pitfall 8: Open-Source Repo Has No .gitignore — Student-Generated Content Will Be Committed

**What goes wrong:** There is no `.gitignore` file in the repository. When a student clones the repo and runs the course, they will create vault notes, daily notes, custom slash commands, and hook scripts. If they fork the repo to share with a friend or contribute back, their personal vault content (notes, drafts, client information) will be included. The `.obsidian/workspace.json` file (which tracks which notes are open) will also diff on every Obsidian session.

**Why it happens:** The project context flags this as "Active" (not yet done) in PROJECT.md. It was likely deferred during initial generation.

**Consequences:**
- Public repos with accidentally-committed personal notes are a privacy risk for students
- `.obsidian/workspace.json` will cause unnecessary noise in git history for anyone who version-controls their forked vault
- Without `.gitignore`, a careless `git add .` before contributing will include everything

**Prevention — minimum viable .gitignore:**
```
# Obsidian workspace state (user-specific, changes on every open)
vault/.obsidian/workspace.json
vault/.obsidian/workspace-mobile.json

# OS metadata
.DS_Store
Thumbs.db

# Environment and secrets
.env
*.env.local

# Any notes the student creates outside the pre-seeded fixtures
# (Note: vault/  itself MUST be included — it's the course content)
```

**Detection:** Run `git status` after opening vault in Obsidian once — any changed files are candidates for `.gitignore`.

**Phase to address:** Distribution readiness phase.

### Pitfall 9: Shell Script Hooks Are Platform-Specific — Windows Students Will Hit Immediate Failures

**What goes wrong:** Module 4.2 teaches students to build `add-frontmatter.sh` — a bash shell script. The README states the course works on "macOS, Windows, or Linux." Bash is not available by default on Windows. The hook configuration in `.claude/settings.local.json` points directly to the `.sh` file. Windows students who faithfully follow module 4.2 will configure a hook that fails silently (or noisily) on every file write.

**Why it happens:** The script was written assuming a Unix environment. The cross-platform claim in the README was not reconciled against the hook implementation.

**Consequences:**
- Windows students hit failure during module 4.2's "Test the Hook" step — exactly the moment the module is supposed to feel magical
- The auto-organize hook stays non-functional for Windows users for the rest of the course (modules 4.3-4.6 build on it working)

**Prevention:**
- In module 4.2, add Windows-specific handling: "If you're on Windows, [either Git Bash / WSL alternative, or Python alternative]"
- OR: Rewrite `add-frontmatter.sh` in Python (cross-platform) with a `.py` extension and `python` invocation
- At minimum: add a note in module 4.1 that hooks use shell scripts and Windows users will need Git Bash or WSL

**Detection:** When playtesting, test on Windows or note the platform gap explicitly in module 4.1.

**Phase to address:** Content quality review / playtest validation.

### Pitfall 10: The "Silent Teaching" Pattern Creates Invisible Failures

**What goes wrong:** Each slash command file (e.g., `start-1-1.md`) instructs Claude to read the teaching script "SILENTLY" before beginning. If Claude fails to read the script — due to file access issues, context length, or misunderstanding — it will start inventing the lesson from its own knowledge. Students will receive an off-script lesson with no indication anything went wrong. The AI may hallucinate vault file names, Alex Rivera details, or teaching steps.

**Why it happens:** The "silent reading" pattern is elegant for UX (no meta-commentary) but provides zero failure visibility. There's no check that the script was actually read before teaching begins.

**Consequences:**
- A module 1.4 "aha moment" improvised from training data rather than the specific four-note sequence designed for it will feel flat or confusing
- A module 3.5 inbox pattern demo improvised without the pre-written capture notes will create different vault content than later modules expect

**Prevention:**
- Add a subtle first-sentence signal to each teaching script: the first Say block's first sentence should be distinctive enough that a reviewer can confirm Claude is on-script vs. improvising
- Consider adding to `.claude/SCRIPT_INSTRUCTIONS.md`: "If you cannot read the lesson module file, stop and tell the student: 'I had trouble loading this lesson. Please try running the command again.'"

**Detection:** During playtest, watch for first words of each module. Compare against Say block. Any deviation means Claude may be off-script.

**Phase to address:** Playtest validation.

### Pitfall 11: 07-MOCs and 08-Published Folders Are Empty — Will Confuse Students on First Vault Tour

**What goes wrong:** Module 1.1 gives students a tour of the vault. Both `07-MOCs/` and `08-Published/` contain no files. When Claude lists these folders as part of the tour (Action: list vault contents), students see empty folders. The script describes these folders as important, but their emptiness undercuts the narrative of a "real vault."

**Prevention:**
- Seed `07-MOCs/` with at least one pre-built MOC that Alex would realistically have (e.g., `AI and Creative Work MOC.md` or `Client Work Dashboard.md`) — this would also resolve Pitfall 1 above
- Seed `08-Published/` with one or two example published pieces (or a note logging what's been published)
- At minimum, module 1.1 should acknowledge empty folders: "These are where your MOCs and published pieces will live — they're empty now, but you'll build the first one in module 2.2"

**Phase to address:** Vault consistency pass.

### Pitfall 13: Student-Visible TODOs in Pre-Seeded Vault Notes Break Narrative Immersion

**What goes wrong:** Three vault files contain raw `TODO:` markers visible to students:
- `vault/04-Drafts/Draft - Digital Boundaries Post 3.md` line 56: `[TODO: closing paragraph...]`
- `vault/00-Inbox/Meeting notes Sarah 03-15.md` lines 16-20: `TODO:` list (revise outline, reach out to Devon, find interview subjects)
- `vault/05-References/Invoice Tracker.md` line 25

The meeting notes TODO is fine — it's plausibly how someone actually takes notes after a call, and module 3.5 uses this note as a teaching fixture. But the Draft file's TODO is a fully exposed editorial instruction that breaks the "authentic content" feeling.

**Prevention:**
- Review each TODO:
  - Meeting notes TODOs: KEEP — realistic and serve as teaching material for the Inbox Pattern module
  - Draft file closing paragraph TODO: either complete the paragraph or convert to `<!-- TODO -->` HTML comment (invisible in Obsidian preview)
  - Invoice Tracker TODO: check if it's intentional teaching content or a generation artifact

**Phase to address:** Content quality review (low priority — only affects immersion, not functionality).

### Pitfall 14: Open-Source Attribution and License Are Missing

**What goes wrong:** The repo has no LICENSE file and no CONTRIBUTING.md. For a course that explicitly wants to acknowledge Tiago Forte's BASB, Zettelkasten, and other frameworks, the absence of attribution documentation is a gap. More practically: without a license, the repo is technically "all rights reserved" by default, which contradicts the open-source intent.

**Prevention:**
- Add MIT or CC-BY-4.0 license (appropriate for educational content)
- Add attribution section to README: "This course builds on concepts from Building a Second Brain (Tiago Forte), the Zettelkasten method (Niklas Luhmann), and tools-for-thought research"
- Do NOT just cite BASB and PARA as if they're public domain frameworks — Forte's work is trademarked; use it as inspiration and acknowledge properly

**Phase to address:** Distribution readiness phase.
